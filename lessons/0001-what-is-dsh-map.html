为什么是这一课

你的毕业项目是为自己领域（CV / 深度学习）构建一个专属 Agent。而 DeepSeek Harness（dsh）就是 DeepSeek 官方交出的「如何造一个 Agent 运行时」的完整答案。读懂它，你就同时学会了：Agent 到底怎么运转、大型开源项目怎么组织、以及别人是怎么把 22 万行代码做成「一切皆可替换」的。

§0先纠正一个预期：这不是 Python 项目

关键事实

dsh 是一个 TypeScript 项目——一个约 220 个包组成的 pnpm monorepo，核心源码约 20 万行 TS。仓库里的 python/ 目录只是一个薄薄的客户端 SDK（通过子进程 + JSON-RPC 调用 TS 运行时），不是系统核心。

别慌。你的两项既有技能迁移性其实很好：

你已经会的迁移到 TypeScript要小心的误导点
C 语法：类型、控制流、函数 TS 的 int x 声明思维直接可用：let x: number TS 是结构化类型（形状一样就兼容），不像 C 只认名字
Python 基础：对象、字典、模块 TS 的对象字面量、import、异步概念都能对上 TS 的 interface 不是 C 的头文件，也不是 Python 的抽象类——它只是「形状描述」，编译后消失

课程会把 TS 语言课拆碎了混在源码课里讲（阶段 1 有两次专门的语言课），你不需要先学完 TS 再读码。

§1「agent harness」是什么东西

你在网页上用 ChatGPT / DeepSeek 对话时，那个网页本身很简单：发消息 → 收回复。但你用 Claude Code、或别人用 dsh 干活时，模型能读文件、跑命令、改代码。是谁在替模型执行这些动作？

harness（运行时框架）就是那个「替模型跑腿」的程序。它做的事可以浓缩成一个循环：

        ┌──────────────────────────────────────────┐
        │                                          │
        ▼                                          │
  组装提示词 ──► 调用模型 ──► 模型返回："请帮我执行工具 X"
        │                                    │
        │                                    ▼
        │                       harness 执行工具 X（读文件/跑命令…）
        │                                    │
        └────────── 把工具结果喂回给模型，再来一轮 ◄┘

dsh 就是这样一个循环的工业级实现：模型适配器、工具注册表、会话日志、甚至这个循环本身，全部是可替换的插件。一句话定位：

一句话定位

dsh = 一个由插件组装出来的 agent 运行时，提供 CLI 和 Web UI，由 DeepSeek AI 开源（MIT 协议，开发者预览阶段）。

§2地图上的三个路标

官方架构文档（docs/architecture.zh.md）很长，但这三个概念是整张地图的骨架，以后每一课都在重复它们：

路标一：一切皆插件

dsh 运行起来就是一棵插件树，由启动时按序叠加的配置层组合而成（组合包 bundle → profile → 用户 patch）。没有需要打补丁的特权内核——想换掉某个模型适配器或工具？把你的插件挂到它旁边就行，原有插件卸载时自动撤销。

路标二：会话日志是唯一事实源（事件溯源）

模型看到的一切对话历史，都来自一个只追加的事件日志（append-only log）。UI 显示、会话 fork、断点恢复、回放测试——全部从这份日志「投影」出来。核心不变量只有一句：模型可见即已记录。

路标三：能力 seam（接缝）

每项能力（文件系统、进程、终端……）都被切成三种角色：接口声明（Service Definition）、实现方（Provider）、使用方（通常是面向模型的工具）。替换一个 Provider，整个产品的行为就变了——比如把文件系统指向远程沙箱，Bash、终端、LSP 就全搬过去了，一行不用改。

§3核心包地图

以下是「产品脊柱」的七个包。现在只需记住名字和一句话职责，每个包以后都有专门的精读课：

包一句话职责ctx 键
core/session只追加的事件日志（事件溯源的心脏）ctx.sessions
core/agentAgent 接口 + 活跃 agent 注册表ctx.agents
core/agent-loop默认驱动器（§1 那个循环的真身）ctx.agentLoop
core/tools工具注册表 + 带把关的执行流水线ctx.tools
core/system-prompt提示词分片 + 工具 schema 的组装ctx.systemPrompt
llm/llm模型适配器接口（seam）+ 流式调用 APIctx.llm
core/scope按 agent 划分注册范围的工具库无（库）

「ctx 键」是什么意思？在 dsh 里，Context（ctx）是所有插件共享的容器，每个服务在它上面认领一个稳定的名字——就像全局插座板上的一个插孔。ctx.tools 就是「工具注册表」这个插孔。细节阶段 2 讲。

§4轮次（turn）与步骤（step）

这是全项目最重要的两个词。官方定义：一个步骤 = 一次模型请求 + 它调用的工具；一个轮次 = 零个或多个步骤。你让 Agent「帮我把这个文件夹的图都标注一遍」，那是一个轮次；期间模型请求了 8 次、调了 15 次工具，那就是 8 个步骤。

turn/start                                ← 轮次开启
  ├─ 从 inbox 领取输入（用户消息 / 注入的上下文）
  ├─ 组装提示词分片 + 工具 schema
  ├─ step/start                           ← 步骤开始
  │     模型请求 → 流式返回 → assistant/message
  │     tool/call → 工具执行流水线 → tool/result
  │  step/end
  ├─ 还欠着工作（工具要求再请求）？→ 下一个 step
  └─ turn/end                             ← 轮次关闭

流程里那些 xxx/yyy 是事件名。dsh 的口头禅是「事件就是扩展点」——三月底你会背下来这张表的。今天只需知道：turn/*、step/*、tool/* 这些会被写进日志（持久事实），而 agent/pre-step、llm/stream 这类是实时的插件挂钩点。

自测：三道题

Q1. 在 dsh 中，一个「步骤（step）」由什么构成？

对。官方架构文档：一个步骤 = 一次模型请求 + 它调用的工具；一个轮次包含零个或多个步骤。这是全项目的基石定义。

Q2. dsh 会话日志的核心不变量是什么？

对。「模型可见即已记录」——凡是抵达模型请求的内容，都必须能从日志重建，且有运行时断言在检查。所以 UI、fork、恢复、回放全都派生自这一份日志。

Q3. 想给 dsh 新增一个面向模型的能力（比如「检测图片中的目标」），应注册到哪里？

对。面向模型的能力 = 工具 → ctx.tools（其 schema 会自动加入提示词组装）。其他选项的归属：新模型提供方 → ctx.llm 适配器；需要持久的事实 → 会话事件。架构文档里有一张「新行为的归属位置」全表。
