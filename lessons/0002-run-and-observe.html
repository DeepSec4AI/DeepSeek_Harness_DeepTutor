DeepSeek Harness 精读 · 阶段 0 · 地图与运行

第 2 课 · 把 dsh 跑起来，亲眼看一个轮次

约 45–60 分钟（含首次构建的等待）｜ 动手实验课 ｜ 前置：完成第 1 课

为什么是这一课

上一课你拿到的是解剖图，这一课是活体观察。从此课程里每个抽象概念（事件、工具调用、插件树）你都能在真实的运行时里指认出来——这是「读懂源码」和「背下名词」的分水岭。

§0准备：装好工具（10 分钟）

  1. Node.js 22.19+ 或 24+（硬性要求：低于此版本 pnpm install 会直接报引擎错误。从 nodejs.org 下载 LTS 安装包，或 winget install OpenJS.NodeJS.LTS）。验证：node --version 输出 v22.19.x / v24.x 及以上。
  2. pnpm（仓库锁定 pnpm@11.7.0，通过 Corepack 启用）：运行 corepack enable（报权限错误就用管理员终端重试，或改用 npm install -g pnpm@11.7.0）。验证：pnpm --version 输出 11.7.0。
  3. Git ≥ 2.26（你应该已有）：验证 git --version。
  4. 可选但推荐：一个 DeepSeek API Key（在 platform.deepseek.com 注册、充值几块钱）。没有 Key 也能完成实验一和实验四，但看不到完整的模型轮次。

以上要求来自官方开发指南 docs/development.zh.md——它判定「搭建完成」的标准是 pnpm run typecheck 成功退出，卡住时以它为准。

§1实验一：从源码构建并启动（30–50 分钟，大部分在等）

为什么用源码构建而不是 npx

本课程的使命是源码掌控：从今天起你手里的仓库就是运行时本体——改源码、改 patch，重启即生效；--dump-config 反映的是你这份源码叠出的树；后续所有课程（改码、写测试、提 PR）都在这同一环境。根 package.json 的 dsh 脚本就是直接用 tsx 跑 apps/cli/src/bin.ts 的源码——从源码运行是这个仓库的一等公民用法。

在仓库根目录依次执行：

cd deepseek-harness
pnpm install        # 5–15 分钟：下载依赖，末尾自动安装 git 钩子
pnpm run build      # 10–30 分钟：编译 host/client 两侧 + Web 前端
pnpm dsh web        # 启动，浏览器打开 http://127.0.0.1:3080

如果配了 API Key，在设置页的「模型提供方」里填入（带截图的官方指南：docs/user/guide/providers.zh.md）。

备线：构建受阻时先用 npx 完成观察（别让工具链卡死学习）

任一步骤报错修不动时，先跑 npx @deepseek-ai/dsh web 保证实验二、三完成——两种方式读写同一个 ~/.dsh，事件观察结果完全一致。但 npx 反映的是 npm 发布版，做不了 §4 的加餐实验；回头修好构建再切换回来（课程期间尽量只用一种方式，避免版本漂移弄脏 ~/.dsh；真弄脏了删掉该目录重启即自动重建）。

§2实验二：触发一个真实轮次（5 分钟）

新建会话，给 agent 一个必须用工具才能完成的小任务，比如：

列出当前目录下的所有文件，数出一共有多少个

在 UI 里观察它工作：你会看到模型「调用工具」（读目录/执行命令），工具返回结果，模型再基于结果说话。这就是第 1 课那张循环图的活体：一次用户输入 = 一个轮次（turn），期间模型请求了几次 = 几个步骤（step）。

§3实验三：解剖会话日志（8 分钟）

刚才那个轮次被完整记录在磁盘上了。去 Harness home 找它：

Windows: C:\Users\<你>\.dsh
macOS / Linux: ~/.dsh

在这个目录里探索，找到会话的 .jsonl 文件（每行一个 JSON 事件的日志），用编辑器打开你刚才那个会话的文件，按顺序找这些事件：

事件含义观察点
turn/start / turn/end轮次边界一个轮次包住了中间所有事件
user/message你的输入原文被记录
assistant/chunk流式碎片一串小事件，拼起来才是完整回复——为了保真回放
assistant/message完整助手消息chunk 流的终点
tool/call + tool/result工具调用与结果成对出现，中间隔着执行过程

三个思考观察（答案都在第 8 课，先自己看）：

  1. 事件是只追加的：你从头读到尾，就是在重放这个会话的时间线。
  2. 每个事件都带一个类似 type 的标签字段——这就是可辨识联合在运行时的样子：先看标签，才知道这条记录有哪些字段。
  3. tool/call 和 tool/result 之间发生了什么？那是 ctx.tools 执行流水线的工作，第 12 课解剖。

§4实验四：看插件树的最终形态（5 分钟）

还记得架构文档那句「各层按顺序应用」吗？现在看活体：

pnpm dsh --profile web --dump-config
# 若 pnpm 抢着解析了参数，改用：pnpm dsh -- --profile web --dump-config

它打印的是bundle → profile patch → home patch → --patch 逐层叠加后的最终插件树，大约 70 行。你看到的任何一行，都可以被你自己的 patch 按 id 替换掉。

观察点（Windows 用户彩蛋）

在这棵树里找 shell 相关的行：Windows 上你会看到 pwsh（PowerShell）工具行，而 Linux/macOS 上同一位置是 bash 行——因为出厂 patch 里写了平台条件表达式，每个系统恰好挂载一个 shell 栈。这就是「patch 不只是开关，还能带逻辑」的实证。

源码构建专属加餐：改一行 patch，看树变化（5 分钟）

首次启动后，~/.dsh/profiles/web/cordis.patch.yml 已自动生成（初始内容是空列表 []）。把它改成：

- id: session-title
  config:
    fallbackMaxWords: 5
    fallbackMaxBytes: 40
    maxTitleBytes: 96

重新 dump，在输出里搜索 session-title——maxTitleBytes 从 80 变成 96。注意我们重抄了整行的全部三个键：patch 是整行替换、不做字段合并，漏抄的键会丢。这是你第一次修改 dsh 的行为——改的是你机器上的存档层，删掉这几行即恢复原状。这个实验也提前回答了上一课的自测第 2 题。

自测：三道题

Q1. 日志中 tool/call 与 tool/result 之间的实际执行，由谁负责？

对。模型只「请求」调用工具（tool/call），真正执行的是 harness 侧的 ToolRuntime 流水线（pre-execute → execute → post-execute），完成后写入 tool/result。模型没有任何执行权——这正是 harness 存在的意义。

Q2. 保存 assistant/chunk 事件（流式碎片）的主要价值是什么？

对。架构文档「会话日志」一节：原始 assistant/chunk 事件保证回放和 UI 保真——不存储任何"加工后的摘要"，回放时看到的就是当时发生的一切。体积换保真，是有意的权衡。

Q3. --dump-config 打印出来的插件树是什么？

对。它打印的是 bundle → profile patch → home patch → --patch 逐层叠加后的最终结果。任何一行都可被更上层的 patch 按 id 替换——这就是你上一课问的「各层按顺序应用」的活体答案。

收尾任务（5 分钟）

  • 确认你完成四个实验并在日志里亲眼见到全部 7 种事件。
  • 去 ~/.dsh/profiles/ 走一圈，亲眼验证你上节课复述的目录结构：web/（package.json 点名 bundles + cordis.patch.yml）与旁边的 node_modules/。
  • 再打开 agent.ts 第 38–46 行的 type Phase。对照你的 jsonl：Phase 的哪个分支的 turn/step 计数，对应你日志里 step 序号的递增？下一课我们开始把你会的 C/Python 语法映射到 TypeScript，目标就是读懂这十行。
  • 术语模糊时翻术语卡；模式对照翻设计模式卡。
